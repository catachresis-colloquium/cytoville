= Settings and accelerator implementation work
:revdate: 2026-11-07

== Owner clarification

Implement the discussed coprocessor backends and usable kernels, not just a
research catalogue. Both adiabatic directions (quantum annealing and reversible,
energy-recovering classical computing) need an early scaffold and harness.
Their research/contribution material belongs at the bottom of Performance,
not as the dominant Settings screen.

Provide top-level Settings tabs:

* Performance: actual backend availability, selection and useful workload
  information; experimental adiabatic work and participation at the bottom.
* Accessibility: high contrast, reduced animation, mono sound and voiceover.
* Video: V-sync, window/border/fullscreen mode and resolution.
* Game: difficulty and an explicit “Inject Evil Weevil” toggle.
* Players: single/multiplayer, AI count, capability and names.
* Server: a contextual Game Server Admin status/details panel and launch/link
  to the actual administration application when used alongside the game.

The original research catalogue in PR 11 was an intermediate implementation
and did not satisfy this clarified Settings design. Do not mark this scope
complete based on disabled buttons, device-name enums or interface declarations.
Keep hosting local; no hardware purchase, external messaging or cloud compute
activation is authorised by these settings.

Ppu, Math, Fpga, Vpu, Qpu and Crypto enum entries are not implementations of

backends to copy from IDApTIK.

Both games should consume the same shared operation implementations with small
game-specific adapters. The accepted operation-first ADR remains the design
authority. Each new backend needs an actual consumer, reference equivalence or
an explicit error bound, resource limits, cancellation/failure handling and
end-to-end measurements. Hardware-dependent validation must name the tested
device/driver; simulated tests do not count as physical-device support.

== Immediate correctness and acceptance

=== Implemented Settings slice, 7 November 2026

The Bevy client now has six top-level tabs. Presentation preferences live in a
separate bounded JSON file (`--settings PATH`), not in authoritative game state.
High contrast, reduced movement/pulsing, music, the presentation-queue hint,
V-sync, borderless fullscreen, window borders and window dimensions control
the actual presentation systems. Video preferences are applied only when their
values change, so changing sound or contrast does not resize the window.

Difficulty, the native Evil Weevil/baseline rival choice, decision budget and
AI name apply to a fresh single-player game. Runtime saves/checkpoints carry
the selected rival configuration; older saves default to the original native
80-decision rival. Existing sessions are not silently reconfigured. Capability
means the explicit 3/12/80-decision budget, not a claim about measured intelligence.

The graphical acceptance script isolates preferences and saves in scratch
storage, visits every tab, reloads preferences, then advances a new game with
the chosen baseline rival. This supplements the existing real map-click,
offline save/reload and loopback TLS host/resume journey. Native desktop
performance and screen-reader acceptance remain separate requirements.

=== Adiabatic harness scope

The collapsed section at the bottom of Performance opens the research guide
and runs bounded reference checks on a background worker. The QUBO is a
one-of-four district travel-cost model from the current content/rules. Its
16 candidates are enumerated and independently checked against minimum cost.
Candidate verification checks variable bounds and recomputes integer energy;
the reference solver has a work budget and cancellation. This is a classical
baseline and provider-result validation seam, not a quantum annealer.

A reversible half-adder retains its two input bits, computes sum/carry into
two clean ancilla wires, then uncomputes. The harness checks all four input
cases; separate tests check inverse execution and invalid gate aliasing.
Logical reversibility on an ordinary CPU is not physical energy recovery.

Run `cargo run -p cytoville-runtime --example adiabatic_harness --locked` for
a JSON receipt including the model, selected candidate, checked energy and
explicit `physical_hardware_tested: false`, `measured_joules: null`. No game
state, network provider or cloud job is changed. There is no hardware driver,
annealing schedule implementation or energy measurement yet. Creusot coverage
remains the three existing resource primitives, not these research kernels.
